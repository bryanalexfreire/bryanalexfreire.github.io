01 E2E · API

Framework E2E y API con Playwright + TypeScript

Problema

Un equipo necesita una base única y mantenible para automatizar flujos E2E y pruebas de API, que cualquier QA pueda extender sin empezar de cero.

Qué construí

Plantilla con Page Objects, componentes reutilizables, fixtures y datos por escenario para E2E, con chequeos de accesibilidad (axe, WCAG 2.1 AA) dentro de los mismos flujos, y un cliente de API tipado con validación de contratos y pruebas negativas, sin navegador.

Resultado

Las pruebas E2E en varios navegadores y las de API corren en cada pull request, y cada ejecución en main publica su reporte HTML con evidencia por paso.

02 API · Performance

API y carga: Karate + k6

Problema

Validar el login y el registro de una API antes de la UI, y saber cómo responde el servicio con carga sostenida.

Qué construí

Suite Karate con escenarios positivos y negativos (usuario inválido, campos vacíos, usuario duplicado) en CI, y una prueba k6 de tasa constante: 20 req/s durante 25 minutos con umbrales de p95 y de tasa de error.

Resultado

p95 de 338 ms (umbral: 1500 ms) en 30.000 peticiones. Ninguna respuesta fue 200: lo reporté como hallazgo, con causas probables y próximos pasos, en lugar de entregar un falso verde.

03 E2E

E2E con evidencia: Serenity Screenplay

Problema

Un flujo de compra completo (login, carrito, checkout) debe probarse en varios navegadores y dejar evidencia que cualquiera pueda revisar sin ejecutar nada.

Qué construí

Serenity BDD con Screenplay y Cucumber, datos desde Excel, Chrome, Firefox y Edge, una captura por paso y un reporte publicado por ejecución.

Resultado

Encontré y documenté un defecto real: el recibo muestra el mes anterior. Quedó registrado como bug conocido: la suite sigue en verde y esa prueba se pondrá en verde cuando se corrija.
